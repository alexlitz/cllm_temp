# Phase 7.F.4 — KV eviction peak memory quantification

Generated by `tools/measure_kv_eviction.py`. Compiled `d_model=736`, `n_layers=18`, `kv_eviction_n_steps=64`. Sampled 10 inputs (5 smoke + 5 from the 1096 corpus, seed=0).

## Methodology

* Compile two models via `compile_full_vm`: `kv_eviction_policy=OFF` and `kv_eviction_policy=STATIC_LIVENESS` (n_steps=64). The byte-identity gate (tests/test_kv_eviction.py) already confirmed the two produce identical logits.
* For each sampled input, build a fresh `LayerKVCache` and call `model(token_ids, kv_cache=cache)`. After the forward, read each layer's `cached_k.shape[2]` — the actual peak `S_kv` for that input.
* Peak K+V bytes per layer = `2 * num_heads * S_kv * head_dim * dtype_bytes` (`dtype_bytes=4` for float32; sparse / compact models still allocate float32 KV cache rows).
* The STATIC_LIVENESS runtime *zeros* dead rows but does not compact the tensor; the **realised drop** column is therefore the fraction of K/V rows that *could* be removed by a future compaction pass (`evicted_positions / total_positions_observed`). The **tensor-shape drop** column is the literal peak-bytes diff between OFF and STATIC_LIVENESS, which is ~0% under today's zero-fill-only implementation.

## Target assessment

Plan target (docs/SAFE_KV_EVICTION_PLAN.md §7.F.2): **≥30% peak KV memory reduction**.

**Gap**: 0.00% realised drop < 30% target.

### Root cause — analyzer coverage bottleneck

The analyzer marks 2584 `(step, KVEntry)` pairs evictable across all dims and `320` cycle-conservative entries. Per `kv_eviction.build_state_from_report` the runtime evictable set is the **AND across every dim name** (a row is evictable only when *every* dim slot at that position is dead). Since the analyzer only classifies a tiny subset of dims as evictable, the per-row AND degenerates to empty for nearly all positions.

Categories preventing evictions:

1. **Dim cycles** (320 entries): dims that participate in a producer/consumer cycle in the declarative IR. The analyzer treats them as live (a later iteration could read them) per `treat_cycle_members_conservative=True`. Top cycle dims (see breakdown above) include the persistent register channels (`REG_PC`, `REG_AX`, `REG_SP`, `REG_BP`) and ALU intermediate dims that read-write through their own self-loop.
2. **Unclassified dims**: dims that aren't TEMP_*, *_PREV_STEP, or *_SCRATCH and have no clear semantic-overwrite path. The analyzer's heuristic categories miss anything that's semantically dead but lacks a naming convention the categoriser recognises.
3. **Per-row AND in `build_state_from_report`**: since the runtime cache row covers *all* dims for one position, ANY live dim at that position keeps the entire row live. So even a single conservative-kept dim (e.g. `REG_PC`) at every position blocks every eviction.

### Concrete fix paths (for Phase 7.F.5+)

* **Per-head/dim cache compartmentalisation**: today's `cached_k[B, H, S, HD]` packs every dim into one row. Splitting into per-(layer, head, dim_group) caches would let the AND degenerate per-group instead of per-position.
* **Cycle-graph refinement**: the current SCC analysis treats any read+write edge between two dims as a cycle. Refining with control-flow / step-index awareness (e.g. `OUTPUT_LO_PREV_STEP -> OUTPUT_LO` is one-shot, not a true cycle) would lift many register channels out of cycle-conservative.
* **Semantic-overwrite category expansion**: the analyzer's third category ("register-marker overwritten by later position write") fires only when the analyzer can prove a dim is written at every later step. Loosen to "written at the very next step" to catch the common `REG_AX` carry pattern.
