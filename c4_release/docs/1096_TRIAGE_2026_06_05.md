## Buckets, ranked by failure count (in measured sample)

### Bucket A — Var/Func MEM_addr1 baseline (~84 failures, 84% of sample)

**Failure signature** (all 84 cases):
```
first_token_divergence=step0:MEM_addr1 expected=0xff neural=0x00
residual_diagnosis=expected-token-never-wins
block=35 layer=25 width=192          ← dynamic-verifier ATTRIBUTION (WRONG)
margin = -5.7 (var_three) to -112M (sub_20 cascade case)
OUT_LO[0] = +2.55 to +5.6e6 (drives 0x00 to win)
OUT_HI[0] = +2.55 to +5.6e6
```

**Affected sub-clusters** (all 0/8 in sample):
- `var_simple_*` (250..274) — `int x = N`
- `var_mul_*` (275..299) — `a=N; b=M; return a*b`
- `var_three_*` (300..324) — three-var sum
- `var_update_*` (325..349) — `x=N; x=x+M`
- `func_add_*` (575..599)
- `func_mul_*` (600..624) — 7/8 fail
- `func_square_*` (625..649)
- `func_max_*` (650..674) — 7/8 fail
- `func_min_*` (675..699) — 6/8 fail
- `if_var_*` (425..449) — 4/8 fail (partial)

**Real attribution per VAR_REAL_ATTRIBUTION_2026_06_05.md:**

The dynamic verifier labels the carrier as `block=35 width=192` =
L34.ffn `post_l9_bz_bnz_pc_override`. A forward-hook block-by-block
decomposition of OUTPUT_LO[0] contribution at the failing prediction
slot shows **block 35 adds +0.000** for all three test programs. The
actual writers of the +2.55 mass are:

| Blk | Sublayer | Op | dLO0 (var_simple_0) | dLO0 (var_three_0) |
|---:|---|---|---:|---:|
|  3 | FFN | `layer3_ffn.mem_byte_0_default_{lo,hi}` | **+0.940** | **+0.940** |
| 14 | ATTN | `layer10_bp_byte_passthrough_bake` head 7 `top_store_query` aux | **+2.000** | +0.000 |
| 26 | ATTN | `layer14_mem_generation` partial counter | -0.391 | -0.159 |
| 35 | FFN | `post_l9_bz_bnz_pc_override` | **+0.000** | **+0.000** |

L3's `mem_byte_0_default` predicts "next MEM addr byte = 0x00" — correct
for positive global addrs, wrong for stack-relative (SP - 8 → 0xff at
byte 1). Block 14 head 7's `top_store_query` aux path (slots 40..47,
`l10_ops.py:1398-1472`) fires INAPPROPRIATELY at MEM-address-byte
positions because its gate predicate
(`MEM_STORE + MEM_ADDR_SRC + CMP+3 + HAS_SE + MARK_STACK0`) is too
permissive — MEM_STORE+MEM_ADDR_SRC alone (without MARK_STACK0) reach
threshold.

**Top-3 fix candidates** (per VAR_REAL_ATTRIBUTION § "Concrete fix
hypothesis"):
1. Add `MARK_MEM = -M` to every slot 40..47 query of
   `_layer10_bp_byte_passthrough_head_spec`. Kills `top_store_query`
   on MEM-address rows definitively. **Risk: low** — MARK_MEM and
   MARK_STACK0 are mutually exclusive via marker registry.
2. Add `H1+4 = -M` (same dim alias as MARK_MEM). Functionally
   identical; same risk.
3. Gate the L3 `mem_byte_0_default` rule on `MEM_ADDR_SRC = 0`
   (only fire for SP-source addrs, not STACK0-source). This addresses
   the +0.94 baseline that drives `var_three_*` (the cluster where the
   block-14 amplifier is dormant); **necessary to cure all 84 cases**,
   not just the high-margin ones.

### Bucket B — 16-bit ALU high-byte cascade (~12 failures in arith
sample)

**Failure signature** (all 12 cases — mul_* / div_* / mod_*):
```
first_token_divergence=step1:SP_byte3 expected=0x00 neural=REG_BP
residual_diagnosis=first-loss-after-symbolic-support
block=14 layer=13 width=1536          ← L13 attn / block-14 attn
margin = -4968
OUT_LO[0] = -497.29, OUT_HI[0] = -497.29
```

Affected:
- `mul_*` (10/50): mul_1,5,9,12,20,29,33,35,36,37 — all show
  `step1:SP_byte3` REG_BP leak.
- `div_*` (2/50): div_5, div_41.
- `mod_*` (2/50): mod_1, mod_7.

This is the **same block 14 head 7 BP-passthrough aux path** as Bucket
A's secondary writer, but the failure manifests on a DIFFERENT slot
(SP_byte3 instead of MEM_addr1). The shared root cause means fixing
Bucket A item #1 (`MARK_MEM = -M`) likely also fixes most of Bucket B,
provided the slot 40..47 gate condition that fires on SP_byte3 also
includes a MARK_MEM positive (which it should, by the same broadcast).

Verification: the divergence appears at `gen=49 abs=93 step1:SP_byte3`,
which is the post-pop stack write. The legitimate `top_store_query`
should only fire on stack-store rows, not pop-cleanup rows. The same
MARK_MEM=−M guard or a MARK_STACK0=+M positive-only gate would close
this surface.

**Top-3 fix candidates**:
1. Bucket A's fix #1 (MARK_MEM blocker on slot 40..47) — single-rule
   fix addressing the shared head 7 aux block; covers both Bucket A
   high-margin cases AND Bucket B's full set.
2. Examine why `top_store_query` aux fires post-pop at step1 — likely a
   stale K-position positive (H1+1 = AX_byte1 marker) that needs a
   step-aware reset. A `STEP_RESET = -M` predicate on slot 40..47
   queries would tie the firing to the actual STORE step.
3. Verify the L13 attn head 7 spec at `l10_ops.py:1398-1472` — confirm
   the aux block was intended for a single specific slot (STACK0 store
   row), and tighten the predicate accordingly.

### Bucket C — CMP/EQ tail emit (10 failures in div/mod 150..249)

**Failure signature**:
```
first_token_divergence=step1:AX_byte1 expected=0x07/0x04/0x02/0x01/0x03 neural=0x00
residual_diagnosis=expected-token-never-wins
block=35 layer=25 width=192          ← L34.ffn `post_l9_bz_bnz_pc_override`
margin = -5.7
OUT_LO[expected_byte] = -0.00, arg=0/+0.94
OUT_HI[0] = +0.94
```

Affected (all div_*/mod_*):
- div_20, div_32, div_39, div_42, div_45, div_46 (6/50)
- mod_3, mod_5, mod_11 (3/50) + sub_20 (1/50)

This is the same `block=35 w=192` label as Bucket A but on a
DIFFERENT slot (`step1:AX_byte1` rather than `step0:MEM_addr1`). The
margin is much smaller (~5.7 vs 26.5). Given that VAR_REAL_ATTRIBUTION
showed L34.ffn does NOT contribute at block=35, the same caveat applies
here: the carrier label may be wrong. Block-by-block decomposition
needed before fix attempt.

**Top-3 fix candidates**:
1. Run `tools/attribute_1096_failure.py --test_id div_20` (or any 0/8
   case) to get a per-block residual snapshot at the AX_byte1 slot.
   Without that, the dynamic verifier's attribution cannot be trusted.
2. Hypothesis: the L18 (block=27 width=42) op that handles
   AX_byte1 emit on multi-byte results may be missing a positive write
   for non-zero hi-byte cases. mul_42 (Bucket E) lands here directly;
   the div/mod cases may share the same surface.
3. If block-by-block trace confirms L18 block=27 is the writer, the fix
   is a one-line L18 FFN rule extension (per ATTENTION_HEAD_IR_MIGRATION_PATTERN
   for the head spec; or `building_blocks_dsl.step_function_rule`).

### Bucket D — SUB 16-bit cascade (1 failure)

`sub_20: 744 - 27 = 717` fails with extreme margin (-112M); the band
contracts show OUT_LO[2] = -5.6e6 (target byte 0x02), OUT_LO[15] = +5.6e6
(0xff). This is the only sub failure in the sample. Likely a one-off
tail bit-32 sign-extension misfiring at the borrow boundary
(744-27 crosses byte boundaries differently than other test pairs).

**Fix priority: low** — single case, may overlap with Bucket C tail
emit once that's fixed.

### Bucket E — mul-specific narrow (1 failure)

`mul_42: 8 * 30 = 240` pins to `block=27 width=42 step1:AX_byte0`. The
L18 narrow tail (42 units) is the writer. Margin -469, OUT_LO[8] = +3.95
(weak), OUT_LO[0] = +97.5 (strong). The 240 = 0xF0 result has byte 0
= 0xF0 — this is the high-byte-bit case where the L18 tail emit
fails to disable the 0x00 default.

**Fix candidate**: a single L18 FFN rule extending the high-bit AX_byte0
output. Likely a clean one-rule fix via `building_blocks_dsl.step_function_rule`
on `(MUL_OP, HIGH_BIT_BYTE0)`.

## Recommended next-round targets (top-3)

### #1 — `_layer10_bp_byte_passthrough_head_spec` slot 40..47 MARK_MEM blocker (single op, single rule)

**Cluster impact**: closes ~95% of measured divergences if the fix
applies uniformly (Bucket A var/func cluster + Bucket B 16-bit ALU
cascade + half of Bucket C).

**File**: `c4_release/neural_vm/unified_compiler/ops/l10_ops.py:1398-1472`
(`_layer10_bp_byte_passthrough_head_spec`).

**Change** (per VAR_REAL_ATTRIBUTION § "Primary surface"):
Add `("MARK_MEM", -M)` to every slot 40..47 query in the
`top_store_query` aux block. Per the dim registry, MARK_MEM is mutually
exclusive with MARK_STACK0 (the slot's intended trigger), so this is
semantically a no-op for legitimate stack-store rows but kills MEM-row
firings.

**Verification**: byte-identity gate via
`compare_symbolic_to_lowered_attn` per
`docs/ATTENTION_HEAD_IR_MIGRATION_PATTERN.md`. Confirm var_simple_0
divergence margin closes from -26.5 to a positive value at the failing
prediction slot.

### #2 — `layer3_ffn.mem_byte_0_default` SP-source gate (single rule)

**Cluster impact**: closes the +0.94 OUT_LO[0] baseline that even
without fix #1's amplifier is enough to break var_three (margin -5.64).
Necessary to cure ALL of Bucket A (not just the high-margin cases).

**File**: `c4_release/neural_vm/unified_compiler/ops/l3_ops.py:372-387`
(rules `mem_byte_0_default_lo` / `mem_byte_0_default_hi`).

**Change**: Add `("MEM_ADDR_SRC", -M)` to the rule conditions so it
fires only when the next MEM byte is for a positive (data-section)
address, not for a stack-relative address. var_simple sets
MEM_ADDR_SRC=STACK0 for its `int x` write; the L3 default for that
case should be 0xff (sign-extension), which is what the L17 partial
counter tries (and fails) to deliver.

**Verification**: same byte-identity gate as #1, plus a per-program
spot check on `var_three_0` (the case where the block-14 amplifier
is dormant and the L3 baseline is the dominant carrier).

### #3 — Block-by-block residual probe on Bucket C/D before any fix

**Cluster impact**: prevents another VAR_REAL_ATTRIBUTION-style
mis-attribution. The dynamic verifier label `block=35 width=192`
matched on Buckets A, C, D, but for Bucket A the real writer was
block 14 (not 35). Buckets C and D have NOT been block-decomposed.

**Procedure**: for `div_20`, `mod_3`, `sub_20`, `mul_42`, run the
`tools/attribute_1096_failure.py` brief + the forward-hook block-by-block
decomposition pattern from `VAR_REAL_ATTRIBUTION_2026_06_05.md`. Confirm
or refute the L34.ffn label before proposing any fix.

**Why this matters**: per memory note
`feedback_single_rule_fixes_are_zero_sum.md`, 0/5 historical
single-rule fix attempts on a mis-attributed carrier have netted
positive. Verifier output > manual diagnosis.
