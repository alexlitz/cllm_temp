### Cluster A — `var_simple_*` (offset 250..274), all 25 cases fail uniformly

Identical residual fingerprint across all 5 traced cases:

```

  expected=0xff neural=0x00
residual_diagnosis=expected-token-never-wins
block=35 layer=25 label='block35 layer=25 width=192'
expected_logit=-5.00  argmax_logit=+21.49  margin=-26.49
OUT_LO[15]=-0.00 arg=0/+2.55   OUT_HI[15]=-0.00 arg=0/+2.55
band_contracts=DRIFT
violations: OUTPUT_LO[15]/active_margin_low (obs=-2.55), OUTPUT_LO[0]/inactive_too_high (obs=+2.55), OUTPUT_LO[10]/inactive_too_high (obs=+0.89), OUTPUT_HI[15]/active_margin_low (obs=-2.55), ...
projection_diag=OUTPUT_LO[expected_low]:unexpected_winner winner=0
```

`abs=119` (NOT 247) is a different MEM_addr1 slot than the one
VAR_THREE_ATTRIBUTION_REPORT.md describes. `block=35 width=192`
corresponds to `L34.ffn: 192 units` from the bake census. Magnitude
of OUT_LO[0]/HI[0] = +2.55 (much bigger than VAR_THREE's +0.78) and
margin = -26.49 (vs VAR_THREE's -5.64) — this is no longer a marginal
under-firing of the 0xFF writer; it's a strong band-0 winner.

### Cluster B — `add_*` (offset 0..31), all 32 cases fail

`run_1096_diag_chunk.sh 0 32` with `C4_1096_TRACE_LIMIT=10` shows the
add cluster fans out across several signatures (not a single carrier):

```
6  step0:SP_byte0     block=34 width=2059    (tail_bit32_result_correction)
1  step1:AX_byte1     block=35 width=192     (L34.ffn — same as var_simple)
1  step0:AX_byte0     block=34 width=2059    (tail_bit32)
1  step0:AX_byte0     block=28 width=792     (likely L31.ffn / format heads)
1  step1:SP_byte3     block=14 width=1536    (likely L18.ffn or L22.ffn)
```

- `step0:SP_byte0 abs=55 gen=11 expected=0x00 neural=0xf8` is the
  classic "uninitialized SP byte0 = 0xF8 leaking from the bootstrap
  return-PC push" — same residue shape as STACK0_STALENESS doc's
  step-4 narrative, except it's now firing at step 0 of an `add`
  program where there is no PSH yet.
- `step1:AX_byte1` is `add_0`'s exact attribution brief signature
  (`expected=0x02 neural=0x00`), and the per-op residual check
  identifies `layer3_carry_forward_attn` as declaring
  `produces['AX_CARRY_HI']='<derived>'` while the residual at the
  AX marker after layer 3 is 1.3e-05 (effectively zero) — i.e. L3
  carry-forward is silently no-op'ing for the add path.

## Net interpretation

Three dominant carriers at HEAD `c3c0dfd0`:

1. **`tail_bit32_result_correction` (L33, block 34, width 2059)** —
   still the dominant carrier for the `add_*` and `SP_byte0=0xf8`
   bootstrap-leak family.
2. **`L34.ffn` (block 35, width 192)** — NEW dominant carrier for
   `var_simple_*` / probably `var_three_*` and other var-family
   programs. Magnitude has GROWN (+2.55 vs +0.78) — a stronger band-0
   writer is now overpowering the canonical 0xFF emitter.
3. **`layer3_carry_forward_attn`** — silent no-op on the add path,
   producing `step1:AX_byte1 expected=0x02 neural=0x00`. The per-op
   residual check pins it on its declared `AX_CARRY_HI` produces but
   the residual is 1e-5 i.e. the op isn't firing.

The smoke result (29 pass / 23 fail / 12 xpassed) is a net improvement
over the prior 25/51 baseline. The 1096 sample (0/32 in each of two
slices) shows the corpus is NOT recovering at the same rate — the
gains are concentrated in cases the smoke gate covers but 1096 does
not. Promoting the 12 xpassed to PASS in the smoke gate is the
lowest-cost win available right now.
