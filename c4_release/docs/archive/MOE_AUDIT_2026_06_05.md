## Question

Blog `BLOG_SPEC.md` §566-568 says "Each opcode only needs a small subset of the FFN ops to complete so it very naturally lends itself to using Mixture of Experts (MoE) routing." V2 of the IR DSL added `opcode_expert_rules` (see `building_blocks_dsl.py:924-990`) as a wrapper that threads an opcode gate through a rule batch.

How much of the *current* model is actually opcode-routed, and where is the unrouted compute?

## How "opcode-routed" is detected

Two routing forms are recognized (both encode an opcode gate, just in different matrices):

1. **W_gate-routed** (canonical `gate="OP_<X>"` in `FFNRule`): the SwiGLU gate row reads OP_<X> with positive weight, so the gate sigmoid only fires when OP_<X> is hot. Built by `gated_write(...)`, `wide_add_rules(opcode_gate=...)`, `wide_mul_rules(opcode_gate=...)`, etc.
2. **W_up anti-opcode blocker** (large *negative* W_up weights on OP_<X>, ~`-1000*S` to `-100*S`): the unit's pre-activation goes deeply negative when any blocked opcode is hot, zeroing the unit. This is the pattern in `l8_ops.py:1937 anti_ops = [...]`, `compiler.py:1078`, and the baked output of `wide_div_rules` at L20-22.

A unit counts as **opcode-routed** if either pattern is present. Detection thresholds: `|W_gate[u,OP_X]| >= 0.05` (canonical) OR `|W_up[u,OP_X]| >= 50.0` (anti-OP / strong condition; well above the ~1.0 marker/data weights of normal conditions).

## Biggest unrouted surfaces (where to focus MoE work)

In descending order of dense-unit count (each unit fires for every opcode):

1. **L29 — 1,869 dense / 1,873 active (99.8%)** — `layer14_temp_clear` + 8 cleanup ops (`layer14_clear_addr_key_pollution`, `layer14_clear_output_corruption`, `layer14_clear_mem_marker_output`, `layer14_addr_key_neural_decode`, three `*_ax_bytes_zero` ops, `layer14_demo_phase6_wave7`). These clear residual scratch — but cleanup is per-opcode (JSR needs JSR-byte-zero, LC needs LC-byte-zero, etc., and they're already split into per-opcode ops). They should be `gate="OP_<X>"`-able trivially. **Action**: wrap each cleanup op's rules in `opcode_expert_rules`.
2. **L22 — 1,536 dense / 1,536 active (100%)** — likely a DIV/MOD merge stage that should inherit the `OP_DIV`/`OP_MOD` gate from L19-21. Worth verifying it isn't already gated via positive W_up conditions that my detector misses (positive condition on OP_X with weight 1.0 wouldn't pass the 50.0 threshold).
3. **L28 — 1,088 dense / 1,112 active (97.8%)** — `ALUShiftComposite`. The L13 SHL/SHR rules use `gate="OP_SHL"`/`gate="OP_SHR"` and bake to L27 with 100% routing, but the parallel `ALUShiftComposite` bake path (efficient-mode select_stage) at L28 puts the routing into W_up data conditions instead of W_gate. **Action**: confirm L28 is residual / dead-path; if it's load-bearing, route via W_gate to match L27.
4. **L18 — 1,028 dense / 1,028 active (100%)** — `layer15_nibble_copy` + L15 attention resize / `layer15_alu_high_byte_relay` / `layer15_store_stack0_sp_byte0_addr` / `layer15_si_mem_addr0_from_stack0` / `conversational_io_output_routing`. These are per-opcode relays (SI is OP_SI; STORE is OP_SC etc.) that are NOT gated on the corresponding OP_<X>. **Action**: easy win — wrap the per-opcode ops with `opcode_expert_rules`.
5. **L33 — 973 dense / 2,059 active (47.3%)** — `tail_bit32_result_correction`. Half-routed; the other half is opcode-agnostic 32-bit sign correction. Some of it may legitimately need to fire for every arithmetic opcode.
6. **L6 — 768 dense** — many ops co-located. The 880 routed are likely the routing FFN itself; the dense are think-protocol/convo-IO ops that arguably should gate on `OP_PUTCHAR`/`OP_GETCHAR`.

## Where `opcode_expert_rules` actually gets used

**Production callers of `opcode_expert_rules`: zero.** The helper was added in commit `4048f3bc` (V2 of the DSL) and only appears in:
- `c4_release/neural_vm/unified_compiler/building_blocks_dsl.py` (definition + `__all__`)
- `c4_release/tests/test_building_blocks_dsl.py` (unit tests)
- `c4_release/docs/IR_DSL_DESIGN.md` and `c4_release/docs/BUILDING_BLOCKS_DSL.md` (design docs)

All current opcode gating comes from:
- `wide_*_rules(opcode_gate="OP_<X>", ...)` — direct opcode_gate parameter (8 call sites in `alu_ops.py`)
- `gated_write(..., gate="OP_<X>", ...)` — direct construction (8 call sites total)
- `dim_ref("opcode_flag", "<X>")` semantic form (4 call sites in l9/l12/l14)
- Anti-OP W_up patterns (compiler-emitted in `compiler.py:1078` for the lev-detector path)

This means the V2 wrapper hasn't been adopted yet — every routed surface still hand-rolls the gate. Adopting `opcode_expert_rules` wouldn't change coverage but would centralize the convention.

## Compute reduction potential

Current dense forward cost ≈ sum of all 38,636 active units. With ideal per-opcode MoE routing the per-token forward cost drops to whatever is gated for the active opcode + the dense floor. Worst-case (OP_MUL): 19,258 / 38,636 = **49.8%**. Best case (OP_JSR, OP_GE, etc.): 9,942 / 38,636 = **25.7%**. Average across all 34 opcodes: 11,217 / 38,636 = **29.0%** — i.e. **71% theoretical FFN compute reduction.**

Caveat: the 76.7% currently "opcode-routed" units are *not* zero-cost. They still multiply against zero gate output, so the matmul itself runs. Realizing the 71% reduction requires either:
- A scatter/gather lowering that physically skips zero-gated rows (per-opcode expert weights packed into separate Linears), or
- A block-sparse W_gate / W_up that fuses zero gating into the kernel.

The blog spec §566 ("avoid unnecessarily computation") implies the first form: separate `nn.Linear` per opcode. That's what `MOE_ROUTING_AUDIT.md` (2026-05-11) already analyzed and what the existing `compact_moe` attribute on `ALUShiftComposite` hints at.

## Size reduction potential

Total FFN parameter capacity = **97,712,202** (97.7M); non-zero = **622,531** (0.64% — already 99.4% sparse, mostly because W_up/W_gate/W_down are heavily zeroed inside their padded `d_model=800` × `ffn_hidden=4096` tensors).

The non-zero count is what matters for actual storage. A per-opcode MoE re-bake would, in the best case, eliminate the `d_model=800` columns that hold zero for non-active OP_<X> — but those zeros are already cheap. The realizable size savings are:

- **Dead capacity reclaim (immediate)**: L7/L8/L13/L14 have `ffn_hidden=1` and 0 active units (dep-anchor stubs). L32 has 1,562 capacity, 26 active (1,536 dead). Right-sizing alone saves ~10 MB of padding.
- **Dense-surface re-routing (5-10%)**: converting the 9,019 dense units to per-opcode experts can shrink the W_up duplication where the same condition is computed for multiple opcodes. But pre-baked opcode-specific lookups (e.g., MUL lo-nibble tables) are already maximally specialized — no compression possible.

**Bottom-line size estimate**: 5-10% non-zero parameter reduction from routing the 9,019 dense units; 50-70% compute reduction at inference with a proper sparse-MoE kernel.

## Caveats

- "Opcode-gated" detection is conservative on the lower bound and may over-count on the upper bound. Positive W_up conditions on OP_<X> with weight ~1.0 (which DO encode opcode-specificity) are below my 50.0 threshold and would push coverage higher. Strong anti-OP weights on non-routing dims (rare) could overcount.
- Per-opcode unit counts in the JSON summary use a heuristic for anti-OP blocker propagation that assumes "any anti-OP pattern + not-blocked == fires"; this is an approximation. For exact per-opcode counts run a symbolic forward pass with a known one-hot opcode and count active gate-outputs.
- L32's 1,562 capacity but 26 active is suspicious — likely a leftover from a default `ffn_hidden=4096` cap on a small op. Worth a separate right-sizing audit.
- The model has 35 blocks but `layout.n_layers == 22` (logical layers) — the model.blocks count includes post-op blocks (the `*_postop_attach` ops live as separate transformer blocks). All FFN coverage numbers count both.
