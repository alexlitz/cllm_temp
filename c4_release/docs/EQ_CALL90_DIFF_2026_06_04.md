## TL;DR

At call 90 the **first divergent block remains block 6** — same as call 7.
However, the **catastrophic amplifier** is **block 34**
(`tail_bit32_result_correction`, 2059 units, the same op that commit
`4e98cfad` partially fixed), which blows the residual delta from
~7,805 to **1.2 billion** in a single FFN.

The L6 seed delta is only ~1.99 at the prediction row — the bug is not L6's
mixing being "wrong" in magnitude; it is that the downstream amplifier chain
(block 27 `layer15_memory_lookup` → block 28 `layer16_lev_routing` →
block 34 `tail_bit32_result_correction`) reads the L6-injected FETCH_HI delta
as evidence and applies 1e9-magnitude writes against it. The amplifier path
gain is ~6e8× per call, which is what destroys lockstep with the deterministic
draft after a small number of EQ-step emissions.

**EQ(5) vs EQ(17) and EQ(42) vs EQ(17) produce identical per-block delta
norms up to 4 decimal places** through block 33, and diverge by ~1% at
block 34. This means **the bug fires uniformly any time `FETCH_HI != 0`**;
there is no per-bit dependence in the seed injection at L6. The block-34
amplifier non-linearity introduces the only bit-pattern sensitivity, and
even that is small.

the catastrophic output; whatever wrong byte the model emits at call 90 is
determined by this block's writes, not by L6's tiny seed.

## EQ(42) vs EQ(17) interpretation

The norms are **byte-identical** through block 33 between the two diffs and
only diverge by ~1% at block 34. This says:

* The L6 seed at block 6 (norm 1.99) is uniform across any
  `FETCH_HI != 0` operand — the bug is not bit-pattern specific.
* The block-27 (memory_lookup) and block-28 (lev_routing) amplifications
  are also uniform.
* Block 34 is the ONLY block whose output magnitude is FETCH_HI-pattern-
  sensitive, and only at the 1% level — i.e. even the final amplifier
  treats the seed as a quasi-uniform "FETCH_HI is non-zero" event.

Combined with `EQ(5,5) → PASS` and `EQ(17,17) / EQ(42,42) → FAIL`, the
failure indicator is exactly `FETCH_HI != 0` (the IMM operand has any high
nibble set). This is consistent with the L6_EQ_VERIFIER_BLIND finding that
the 16 `_layer6_imm_fetch_to_output_hi_k` routing rules are
*architecturally correct as written* — they DO mix FETCH_HI into AX_CARRY_HI
+ OUTPUT_HI_THIS_STEP at AX-marker positions, and that mixing is the
intended path. The 1.99 seed at block 6 represents this intended mixing,
not a bug.

The bug is the downstream amplifier chain treating that intended 1.99-norm
mixing as evidence for 1e9-strength writes.

## Cross-reference to commit `4e98cfad` (`tail_bit32_result_correction`
fix)

Commit `4e98cfad` added a `("HAS_SE", 10.0)` condition + raised threshold
by 10 on the rule `tail_sp_marker_byte0_f8_from_initial_stack_exact`. That
fix specifically targeted **step 0** firing (`HAS_SE=0` → rule cannot meet
threshold), per the doc body:

> Apply the BZ step-0 guard pattern (commit 877335ae): require HAS_SE=1 to
> fire by adding the +10 step0_guard_weight and bumping the threshold by
> the same amount. This kills the rule on step 0 entirely.

The EQ(17) corruption is at **steps ≥ 1**, where HAS_SE=1 and the new
guard does NOT fire. So the step-0 fix is preserved by this analysis but
does not touch the surface in play here.

The wider `tail_bit32_result_correction` op contains many sibling rules
beyond the `tail_sp_marker_byte0_f8_*` family — the L10 ops file at
`_tail_bit32_result_correction_rules()` defines ~30 helper rule families.
The block-34 explosion implicates at least one of:

* `tail_sp_byte1_ff_from_initial_stack_exact` (l10_ops.py:5298) — gates on
  `IS_BYTE=5.0` + `H1+2=20.0` with 1e9-magnitude H1 blockers. If FETCH_HI
  contamination leaks into any H1 lane at an AX-byte-1 emission row, the
  rule's blockers fire with their 1e9 magnitude.
* `tail_sp_marker_byte0_f8_from_initial_stack_exact` (l10_ops.py:5252) —
  fired at step 1+ unchanged by the 4e98cfad fix (the fix only guards
  step 0). At step 1+ the rule is INTENDED to write `0xF8` at SP-marker
  rows, but reads `OUTPUT_HI_THIS_STEP+14 = -1000.0` and `H1+0..4 = -1e9`.
  Any FETCH_HI leak that raises H1 or OUTPUT_HI_THIS_STEP+14 at an
  AX-byte-1 row gets a 1e9-magnitude wrong-byte write.

## Concrete fix surface (with verifier-output evidence)

Per the L6_EQ_VERIFIER_BLIND finding, `verify_rule_strength` on
`layer6_routing_ffn` returns 0 strength violations because 0/1315 rules
carry `scope`/`dominates_at` annotations. The same is true for
`layer15_memory_lookup` (kind=attn, no FFN rules) and
`layer16_lev_routing` (FFN). However, the block-34 op
**`tail_bit32_result_correction`** is the only op in the catastrophic
chain that DOES use annotated rules — the
`tail_sp_marker_byte0_f8_from_initial_stack_exact` rule at l10_ops.py:5252
explicitly carries `scope="mark == SP"` and
`dominates_at={"OUTPUT_LO": "mark == SP", "OUTPUT_HI_THIS_STEP": "mark == SP"}`.

This means `verify_rule_strength` CAN reason about
`tail_bit32_result_correction` rules. The recommended unblock path:

1. **Run `verify_rule_strength(make_tail_bit32_result_correction_op(),
   registry, ...)`** with the EQ(17) seed delta as a probe — specifically,
   measure whether any rule's claimed `dominates_at` predicate
   (`mark == SP`, `is_byte`, etc.) survives at an AX-byte-1 emission row
   when the H1 lanes carry +1.99-magnitude FETCH_HI leakage. The expected
   "they-think-they-dominate-but-don't" pair is between
   `tail_sp_byte1_ff_*` (scope `is_byte`) and the L8/L10 same-position
   OUTPUT_HI writers — if any AX-byte-1 row also passes the `is_byte`
   predicate when the L6 seed delta is present, the rule fires at the
   wrong row class.

2. **Narrow to the L6 seed dimensions.** The block-6 → block-27 jump
   (1.99 → 80, 40x) implicates `layer15_memory_lookup`'s K/Q binary
   address lookup; the 1.26e10 `|W_q|` is in the binary-address-lookup
   primitive (`binary_address_lookup_attention` at line 10 of
   `ops/l15_ops.py`). If any of the L6-leaked residual dims overlap
   with the `ADDR_KEY` band (residual dims 206..254), the binary lookup
   will pick a wrong memory cell and amplify by 1e10. Check whether
   `layer6_attn` head 1 writes any AX_CARRY_HI dim that aliases into
   the ADDR_KEY band (`AX_CARRY_HI = [344:360]` per the CONTRACT OVERLAP
   dump; ADDR_KEY = [206:254]; they do not directly overlap, so the leak
   path must be indirect via L7-L13 propagation).

3. **The cheapest "guard" fix:** raise `tail_sp_byte1_ff_from_initial_stack_exact`'s
   `IS_BYTE` threshold from 5.0 (line 5304) by adding an additional gate on
   `MARK_AX = -1e9` to ensure the rule cannot fire on AX-marker rows. This
   is the same pattern as the existing `MARK_AX=-1e9` blocker on the SP
   variant (line 5271). If `tail_sp_byte1_ff_*` currently lacks a MARK_AX
   blocker, FETCH_HI contamination at AX-byte-1 rows is the symmetric
   complement of the step-0 leak that 4e98cfad fixed.

**Do NOT** patch any rule without first running step 1 — per
`feedback_single_rule_fixes_are_zero_sum.md`, blind L6/L10 patches are 0/5
historically. The verifier sweep on `tail_bit32_result_correction` is the
first time the EQ regression has a measurement target that the verifier
can actually reason about (because that op IS annotated).

## What this rules out / de-prioritises

* **L6 attention or routing FFN as the patch site.** The L6 mixing is
  intended and small (1.99 norm seed). Patching L6 to suppress FETCH_HI
  flow would regress every IMM-with-high-nibble code path system-wide.
* **`layer15_memory_lookup` as the patch site.** Its 40× amplification is
  the binary-address-lookup design — large `|W_q|` is intentional for
  one-hot K-Q matching. Tweaking it would regress memory I/O.
* **Pure logit-competition fixes (head.bias, head_bake).** Confirmed
  upstream by STACK0_ABLATION_2026_06_04.md; that conclusion is
  unchanged by the call-90 analysis. By the time the residual reaches
  the head it is at 1e9 magnitude — no bias tweak can win that race.

## What stays unresolved

The verifier needs L15 / L16 / non-`tail_sp_*` L10 rules annotated for
full coverage. The current best lead is whether `tail_sp_byte1_ff_*`
fires at AX-byte-1 emission rows; verifying that without an annotation
sweep requires either step-3 of the fix-surface (manual scope blocker
addition + smoke regression test) or a downstream contribution-algebra
probe (`decl_verifier._collect_ffn_rules_from_op(
make_tail_bit32_result_correction_op())` + per-rule activation under a
synthetic AX-byte-1 row with FETCH_HI=1 residual).

## Confidence

* **High** that the catastrophic amplifier is block 34
  (`tail_bit32_result_correction`). Direct measurement: 1e3 → 1e9 jump
  in a single block, FFN hidden = 2059 matches the op's allocator
  signature.
* **High** that the L6 seed (1.99 norm) is intended, not a bug to
  fix at L6. EQ(5) vs EQ(17) and EQ(42) vs EQ(17) produce byte-identical
  L6 seeds, confirming the seed is `FETCH_HI != 0`-uniform and small.
* **High** that the failure mode `FETCH_HI != 0` generalises beyond
  EQ(17) and EQ(42). Per L6_EQ_VERIFIER_BLIND, EQ(42) also fails; both
  programs reach block 34 with byte-identical residual deltas through
  block 33.
* **Medium-high** that adding `MARK_AX = -1e9` blocker to
  `tail_sp_byte1_ff_from_initial_stack_exact` (rule at l10_ops.py:5298)
  is the smallest-surface fix. It mirrors the existing MARK_AX blocker on
  the SP variant and applies the same "wrong row class can't fire" guard.
  Verification required before patch: confirm via
  `_collect_ffn_rules_from_op` that the rule has no existing MARK_AX
  blocker, and that AX-byte-1 rows under FETCH_HI leakage pass the
  `IS_BYTE >= 5` predicate.
* **Low** that the verifier alone (without scope annotations on L15/L16)
  can fully localise the block-27 → block-28 component of the
  amplification. Block 34 has annotations and is the right starting
  point; if the patch there closes the smoke regression, the L15/L16
  amplification becomes moot.
