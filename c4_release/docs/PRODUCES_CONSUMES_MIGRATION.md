# `produces` / `consumes_fresh` Migration Plan

**Goal**: make the optional `produces` / `consumes_fresh` declarations on
`Operation` mandatory and authoritative across the ~170-factory op corpus
in `c4_release/neural_vm/unified_compiler/ops/`. Once every op declares
its in-step semantic read/write surface, the compiler can statically catch
the `OPCODE_BYTE_LO`-class bug (cross-step read of a same-step writer)
that the step-0 safety added in `ef6ef561` currently only *warns* on.

This document captures (1) the current coverage audit, (2) the
derivation rules and tool, (3) the per-wave migration plan, and (4) the
end-state validation gate.

## Background

`Operation` declares two read/write surfaces:

| Surface | Status | Used by |
|---------|--------|---------|
| `reads` / `writes` | MANDATORY | scheduler dep graph (`LayerCompiler._topological_sort`) |
| `produces` / `consumes_fresh` | OPTIONAL (3+8+4 / 166 ops as of 2026-06-03) | `decl_verifier` staleness analyzer (`LayerCompiler.build_staleness_registry`) |

The semantics, per `ARCH_LEAKAGE_FIX_PLAN.md` and the docstrings on
`Operation`:

* `produces[dim] = register_slot` — declares the op writes this dim AT
  the named step-relative register slot (e.g. `"AX_byte0"`, `"PC_marker"`)
  and that the residual at that slot is the SAME-STEP value, not a
  cross-step leftover.
* `consumes_fresh[dim] = register_slot` — declares the op reads this
  dim's SAME-STEP value at the named slot. The analyzer warns when a
  consumer's `(dim, register)` has no earlier-phase producer in the same
  step (i.e. the consumer is reading a cross-step / leftover value).

Making the surfaces mandatory + authoritative would let the compiler
fail at compile time on every `OPCODE_BYTE_LO`-style stale-read bug.

## Derivation rules (`tools/derive_produces_consumes.py`)

For each op whose `compiler_ir` has at least one `FFNRule`:

1. `produces[name] = slot` — `name` = every `DimRef.name` that appears
   in `FFNRule.writes` across every rule of every layer of
   `op.compiler_ir`. `slot` is currently a heuristic guess (see slot
   inference below).

2. `consumes_fresh[name] = slot` — `name` = every `DimRef.name` that
   appears in a rule's `conditions=` / `gate=` / `gate_terms=` AND that
   the op also declares in its `reads` set AND that is NOT on the
   `_CROSS_STEP_DURABLE` allowlist (CONST / IS_BYTE / BYTE_INDEX_* /
   MARK_* / MEM_VAL_B* / EMBED_* / H0 / H1 / OP_LEV / OP_ENT / OP_RET).

3. Imperative ops (`compiler_ir` is None or has no rules) yield empty
   sets and are flagged for per-case migration.

### Slot inference (deliberate gap)

The auto-derived slot is a placeholder (`target_op_name` / `semantic_label` /
`layer_idx`). The *real* slot convention per existing annotations is a
step-relative register/byte name:

* `"AX_byte0"` / `"AX_byte1"` / `"AX_byte2"` / `"AX_byte3"` — the four
  multi-byte ALU slots within the AX register.
* `"PC_marker"` / `"AX_marker"` / `"SP_marker"` / `"BP_marker"` — the
  step-relative anchor positions used by PC/AX/SP/BP-pinned writes.
* `"STACK0"` / `"STACK1"` / `"STACK2"` — call-frame slots.

The derived `produces` / `consumes_fresh` therefore needs human review
to map each dim to the correct slot. The POC at `make_layer14_temp_clear_op`
demonstrates the workflow.

### Known false positives

* `consumes_fresh` over-reports when an op reads a dim that is
  *intentionally* a cross-step durable (rare for IR rules — the
  `_CROSS_STEP_DURABLE` allowlist covers the common offenders).
* `produces` under-reports for ops whose declarative bake writes via an
  imperative side-path (e.g. embed cells, attention rows). The
  imperative wave (below) covers these.

## POC: `make_layer14_temp_clear_op`

Derived via `python3 tools/derive_produces_consumes.py
c4_release.neural_vm.unified_compiler.ops.l14_ops:make_layer14_temp_clear_op`:

```
derived produces (2):
    'OUTPUT_HI_THIS_STEP': 'layer14_mem_generation',
    'TEMP': 'layer14_mem_generation',
derived consumes_fresh (2):
    'AX_CARRY_HI': 'layer14_mem_generation',
    'TEMP': 'layer14_mem_generation',
```

Slot-mapped manually after reading the FFN rule program (4 units: TEMP+0
at PC marker, TEMP+8/9 position-uniform, OUTPUT_HI+0..15 at AX_byte0):

```python
produces={
    "TEMP": "PC_marker",
    "OUTPUT_HI_THIS_STEP": "AX_byte0",
},
consumes_fresh={
    "TEMP": "PC_marker",
    "AX_CARRY_HI": "AX_byte0",
},
```

After the POC, the audit shows `both: 2 -> 3` and `l14_ops` moves from
`{both: 0, none: 12}` to `{both: 1, none: 11}`.

## Wave plan

Estimated 8 waves to reach 100% coverage + flip the analyzer to fail-hard:

| Wave | Scope | Count | Strategy |
|---|---|---|---|
| 1 | IR-bearing layer ops with single dominant slot (l6/l7/l8/l11/l12/l14/l16) | ~16 | derive + slot-review + commit |
| 2 | Remaining IR-bearing layer ops (l9/l10/l13/l15) | ~7 | derive + slot-review + commit |
| 3 | `control_flow_heads` + `flag_gated_ops` (mostly single-rule branch ops) | ~13 | derive + per-op review |
| 4 | `l0_ops` / `l1_ops` / `l2_ops` / `l3_ops` / `l4_ops` / `l5_ops` token-feed pipeline | ~21 | mostly empty (`writes` are cross-step embeds) — declare empty |
| 5 | `alu_ops` lookup tables | ~42 | declare empty `produces` (tables are constant) — mostly no-op |
| 6 | `model_ops` (embed, tie, unembed) | ~13 | per-case; many produce embed/cross-step values, empty |
| 7 | `user_input_ops` + remaining imperative | ~6 | per-case |
| 8 | Flip analyzer to fail-hard (raise from warn); make `produces`/`consumes_fresh` mandatory in `Operation.__post_init__`; update tests | 1 PR | enforce |

Estimated 8 waves total.

After wave 8, the compiler will refuse to dispatch an op that reads a dim
in a slot with no earlier-phase same-step producer — catching the
`OPCODE_BYTE_LO` class of bugs at compile time instead of at validator
divergence.

## Tooling

* `tools/audit_produces_consumes.py` — coverage report (rerun after each
  wave to track progress).
* `tools/derive_produces_consumes.py` — per-factory derivation; usable
  as a CLI or as a library (`from tools.derive_produces_consumes import
  derive_for_op`).

## Validation gate (wave 8)

The flip-to-fail-hard wave requires green:

1. `pytest c4_release/tests/test_declarative_verification.py` (all
   modes: A, B, B+).
2. `C4_VERIFY_DECLARATIONS=1 pytest -m verify_declarations` (the slow
   Mode B+ multistep produces verifier).
3. Existing smoke + integration sweeps unchanged (`alu_mode='lookup'`
   build).
