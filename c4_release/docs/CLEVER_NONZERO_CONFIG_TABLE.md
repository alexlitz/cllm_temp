## Counting rule (honored exactly)

**TOTAL non-zeros = every position in every weight tensor that holds a non-zero
value, REPLICAS COUNTED** — a value repeated across dims or layers counts each
time; this is *not* a count of distinct values. This is the rule the measured
census already uses (a 51-entry decode cell replicated across 20 MUL layers counts
1,020, not 51).

The per-family REAL-cell footprints (measured from the byte-exact cells):

| cell | nonzero | breakdown |
|---|--:|---|
| arith/div/mul decode cell (whole_value, decimal-10 candidates) | **51** | embed 12 + Q/K/V/O identity 16 + candidate table 19 + 4 scalars |
| bitwise LUT triple OR+AND+XOR (16×16 nibble) | **2,974** | OR 1,023 + AND 943 + XOR 1,008 |
| memory CAM | **10** | 8 nibble match-lanes + temperature + value-read |
| framing / embed | — | 12 token-embed + 10 LM-head + 4 per stored layer |
| digit_extract radix-`r` decode cell | **32 + (2r−1)** | the 32 radix-free part + a radix-`r` candidate table (`r` centres + `r−1` values) |

The **only radix-coupled piece** is the difference-min candidate table: `r` centres
(`d + 0.5`, all > 0 → `r` nonzero) + `r − 1` values (the `0` value is a zero entry)
= `2r − 1` nonzero. Decimal (`r=10`) → 19, matching the measured 51-entry cell.

## How each axis moves the count

- **precision** — sets the exact-integer ceiling (`int8` 127 · `bf16` 256 · `fp16`
  2048 · `fp32` 2²⁴ · `fp64` 2⁵³ · `fp128` 2⁶⁴). It does **not** directly change the
  non-zero count (the cell tensors are the same shape); it *bounds the radix* (below)
  and it is what makes a config byte-exact or a mere throughput proxy.
- **radix** — bigger radix ⇒ fewer digit-extraction layers (`depth =
  ceil(bits / log₂ radix)`) but a bigger per-layer candidate table (`2r − 1`). In an
  **unrolled** stack the table is replicated per layer, so the two fight — see the
  depth↔radix curve (§4).
- **extraction** — `whole_value` holds the whole operand in one scalar (decimal-10
  readout, depths 11/10/20 for arith/div/mul); `digit_extract` is a radix-limb decode
  (depth = radix-limbs of the result width); `nibble` is the production 4-bit lanes
  (== radix 16, depth 8 over 32 bits). `nibble` is only reported at radix 16 — it *is*
  radix-16 by construction; other radices are a category error.
- **mode** — where the depth is stored:
  - **unrolled** (standard feed-forward, stock Qwen2): every family's digit places are
    DISTINCT stored layers; `n_layers` = summed per-family depth; replicas counted.
  - **looped** (Universal-Transformer): one stored cell per machinery member (ingest+arith
    / div / mul decode + bitwise LUT + CAM), each stored ONCE, re-applied `depth` times.
    Only legal for a *looped* architecture — not stock feed-forward Qwen2.
  - **forwards_per_step = F** (the vanilla autoregressive resolution): `L = ceil(D / F)`
    physical stored layers re-invoked `F` times per VM step. Fits a stock 24-layer
    budget, plain AR loop, compute-conserved (`L·F ≈ D`).

Machinery families and their unrolled depths (the `n_layers` a family contributes):
`arith` (ADD/SUB/CMP/SHL/SHR + frame + memory-address adds) · `div` (DIV/MOD) · `mul`
(64-bit product) · `bitwise` (OR/XOR/AND, depth 8) · `memory` (CAM, 1) · `trivial`
(IMM/PSH/NOP/HALT, 1). The **active op is data-dependent**, so a standard feed-forward
net must CONTAIN every family — hence the depths SUM.

**Reading the table.**
- **The bitwise LUT dominates** every unrolled row (23,792) — floats have no bit
  operations, so OR/XOR/AND genuinely need a per-nibble 16×16 lookup, replicated over
  the 8 nibble places. Once arithmetic collapses into the float, the bitwise floor is
  the whole story of the unrolled totals (all ~26k–29k, plus/minus the arith depth).
- **Arithmetic is tiny** (153 looped / ~2,091 unrolled for the decimal whole-value
  ISA): the whole-value + difference-min collapse is real — ADD/SUB/MUL/DIV/MOD/CMP/
  shift/frame share ONE ~51-nonzero cell.
- **looped ≈ 8× smaller than unrolled** because it stores each cell once instead of
  replicating per place (3,183 vs 26,119 at fp64 whole-value) — but that is only honest
  for a Universal-Transformer, and it does **not** shrink the KV cache (see the measured
  doc §7).
- **The huge-radix rows** (`fp64 r=67,108,864`, `fp128 r=4,294,967,296` — each
  precision's max-safe radix) are valid but degenerate: a billion-entry candidate table
  buys only depth 17/14. They are the "radix = 2³²" absurdity §4 warns about, kept in
  the table to show the trend continues to its limit.
- **`forwards_per_step=3`** (last row) re-books the 51-layer whole-value depth into
  `ceil(51/3)=17` physical stored layers — fits a stock 24-layer budget as a plain
  autoregressive loop. Its stored footprint (9,552) sits between looped and unrolled:
  it stores 17 physical layers (not 6 cells, not 51), so it replicates the bitwise LUT
  3× (8,922) rather than 8× or 1×.

## Pruned configs — the precision↔radix coupling

A whole-ISA config uses ONE radix, so it must satisfy EVERY op; the **binding op is the
tightest** (MUL's `r²·L`-class column peak, then DIV's `r²`). `opconfig.validate` /
`acc_max` reject a radix whose accumulator overflows the precision's exact-int ceiling.
`whole_value` extraction is exempt (the whole operand lives in one scalar; radix is only
the readout base, no limb decomposition). **8 configs pruned:**

| pruned config | reason |
|---|---|
| int8 r16 nibble | MUL accMax 1904 > int8 ceiling 127 |
| int8 r4 digit_extract | MUL accMax 188 > int8 ceiling 127 |
| int8 r16 digit_extract | MUL accMax 1904 > int8 ceiling 127 |
| int8 r256 digit_extract | ADD accMax 512 > int8 ceiling 127 |
| fp16 r256 digit_extract | MUL accMax 260864 > fp16 ceiling 2048 |
| bf16 r16 nibble | MUL accMax 1904 > bf16 ceiling 256 |
| bf16 r16 digit_extract | MUL accMax 1904 > bf16 ceiling 256 |
| bf16 r256 digit_extract | ADD accMax 512 > bf16 ceiling 256 |

So `int8` can only carry radix 2 (MUL's r²-class peak overflows at r≥4), and `bf16`
tops out at radix 4 for a *pure single-precision* whole ISA. **The measured
min-walltime shape uses a mixed-precision override** — `bf16` body with MUL bumped to
`fp16` (`opconfig.min_walltime_config`) — precisely to make `bf16 r16` valid where a
pure-bf16 r16 is pruned here. This table reports the honest *single-precision*
whole-ISA validity; the measured doc's 42-layer bf16-r16 corner is the mixed-precision
relaxation. `whole_value` is valid at every precision (no coupling), which is why the
byte-exact min-param build is fp64-body + fp128-MUL whole-value.

## Depth ↔ radix ↔ nonzero (representative op: DIV, 32-bit)

Bigger radix ⇒ fewer layers (`depth = ceil(32 / log₂ r)`) but a bigger candidate table
(`2r − 1`), replicated per layer in an unrolled stack:

| radix | depth | candidate table | per-layer nz (32 fixed + cand) | **TOTAL nz (unrolled chain)** | candidate-only (depth × radix) |
|--:|--:|--:|--:|--:|--:|
| 2 | 32 | 2 | 35 | 1,120 | 64 |
| 16 | 8 | 16 | 63 | 504 | 128 |
| 256 | 4 | 256 | 543 | 2,172 | 1,024 |
| 65,536 | 2 | 65,536 | 131,103 | 262,206 | 131,072 |

Two things this shows:
- **The pure candidate-table cost grows as `depth × radix`** (last column: 64 → 128 →
  1,024 → 131,072) — the table grows LINEARLY in radix while depth falls only
  LOGARITHMICALLY, so the product GROWS. Big steps trade depth for width and net *more*
  candidate weights.
- **The full per-layer cell** carries a fixed 32 non-candidate weights (embed / QKVO /
  scalars) on TOP of the candidate table, so the *total* has a shallow minimum near
  radix 16 (504) where the deep-chain fixed overhead (radix 2: 32 × 32 = 1,120) has been
  paid down but the candidate table hasn't yet exploded. Past radix 256 the candidate
  table dominates and the total climbs without bound (radix 65,536: 262,206).

**Takeaway:** minimum non-zeros is at *small-to-moderate* radix + deep (radix 2–16),
never at big-radix/shallow — the shallow high-radix corner is a width blow-up. This is
the same trade the blog note §3 states; the extra nuance here is that the fixed
per-layer overhead makes radix ~16 the total-minimizer, while the *candidate-table*
component alone is monotone in radix.

## The two Pareto corners

| corner | config | mode | **TOTAL nonzero** | walltime (measured, §ref) |
|---|---|---|--:|---|
| **MIN-NONZERO (byte-exact / canonical)** | fp64/fp128 whole_value | looped (UT) | **3,183** | 1.081 ms/step (slowest datapath, `CLEVER_REALTIME_MEASURED` §6) |
| **MIN-NONZERO (absolute, in-sweep)** | int8/bf16/… r2 digit_extract | looped (UT) | **3,135** | — (low-radix candidate table `2r−1 = 3 < 19`; byte-exact only if the accumulator fits the ceiling) |
| **MIN-WALLTIME** | bf16 radix-16 digit_extract (MUL→fp16) | unrolled (42L) | **25,624** | **0.009 ms/step** (fastest realizable, `CLEVER_REALTIME_MEASURED` §6) |

- **MIN-NONZERO** buys the smallest weight count but runs on the card's slowest datapath
  (fp64 whole-value, 1.08 ms/step, ~120× the bf16 corner). The doc-canonical figure is
  **3,183** (fp64/fp128 whole-value looped); the sweep's *absolute* minimum is **3,135**
  (a low-radix looped digit-extract, whose `2r−1` candidate table undercuts the decimal
  19 — genuine, but byte-exact only when the precision ceiling holds the op accumulator).
- **MIN-WALLTIME** is the fastest realizable config (bf16, 0.009 ms/step) but stores ~8×
  more (25,624 nonzero at 42 unrolled layers). The min-walltime total differs slightly
  from this table's pure-bf16-r16 pruned entry because it is the mixed-precision
  (MUL→fp16) build the measured doc benched.

They are genuinely opposite corners of the same frontier (params-down ↔ walltime-down);
`CLEVER_REALTIME_MEASURED.md` shows **neither reaches Doom realtime** as a realizable
vanilla feed-forward transformer — the wall is the full 896-wide per-step stack, not the
non-zero count.
