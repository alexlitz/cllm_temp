# Var-Cluster Attribution — JSR Step 0 MEM_value1 (2026-06-07)

Wave 1 Cluster C1 follow-up: the prior memory note
`project_var_failure_mode_shifted` (2026-06-02) predicted the divergence
had migrated to L3 block=3 gen=13 SP_byte2 OUTPUT_LO[1]-vs-[0]. As of
2026-06-07 that prediction is stale — the failure has shifted again.

## Current divergence (verifier)

Running `tools/attribute_1096_failure.py` against `var_simple_0` and
`if_var_0`:

| Test         | step | slot       | expected | neural | suspect dims         |
|--------------|------|------------|----------|--------|----------------------|
| var_simple_0 |    0 | MEM_value1 |     0x00 |   0xff | OUTPUT_LO, OUTPUT_HI |
| if_var_0     |    0 | MEM_value1 |     0x00 |   0xff | OUTPUT_LO, OUTPUT_HI |

Both programs start with the function-prologue **JSR imm=3** at step 0,
pushing the return PC `0x0a` to `SP=0xFFFC`. Symbolic MEM_value bytes
are `(0x0a, 0x00, 0x00, 0x00)` — i.e. the high three bytes are zero.
Neural emits 0xff at byte 1.

This is the **same divergence shape** documented in
`docs/VAR_CLUSTER_JSR_PATH_FINDINGS_2026_06_06.md` but it has now moved
back from `MEM_addr2` (post the 06-06 partial fix) to `MEM_value1`.
Either the 06-06 patch was reverted/superseded, or a same-layer
competitor has shifted the surviving error to a different MEM slot.

## First-mismatch op (verifier)

```
op:        layer3_carry_forward_attn
layer_idx: 3
reason:    declares produces['OUTPUT_HI']='<derived>' but residual
           abs-max at AX-marker pos=N after layer 3 is ~9.6e-22 (< 1e-03)
```

This is a **dynamic-verifier false positive** for step 0: head 5
(`_ax_full_relay_head_spec`, l3_ops.py:1427) reads
`OUTPUT_HI_PREV_STEP` via attention back to the prev-step AX-marker
row. At step 0 there is no prev step, so the residual *should* be
zero. The verifier flags this as "claimed but silent" because it
cannot distinguish step-0 from a stale-residual bug.

## True writer of MEM_value1=0xff

Not localized by the verifier at step 0. Candidate writers per the
brief's "all candidate ops for suspect dims" list, intersected with
JSR-step-0 firing predicate:

- `layer14_mem_generation` — emits MEM bytes; has `-1.0` OUTPUT cancel
  at byte 0 only (l14_ops.py:528-529, 622-623). Bytes 1-3 are emitted
  by V→O sum at `OUTPUT_LO+k`/`OUTPUT_HI+k` for k=0..15. For
  4-byte-aligned address values the high three bytes should resolve
  to 0x00.
- `layer14_jsr_mem_default_suppress` — added 2026-06-06 to suppress
  the L3 MEM DEFAULT +0.940 baseline at JSR/PSH/ENT store positions.
  Earlier finding: this overcancels at MEM_addr2/MEM_addr3 (true
  bytes are 0x00 there). Same shape would overcancel MEM_value bytes
  1-3 if predicates overlap; **net result is `0xff` emerging from
  the un-cancelled L3 DEFAULT minus competitor pushes.**
- `layer16_lev_routing` — emits LEV bytes; should not fire on JSR.
- `tail_bit32_result_correction` — touches OUTPUT bytes.

## Single-rule fix is not clear

Per memory note `feedback_single_rule_fixes_are_zero_sum`, narrow
DSL patches in this cluster have netted **0/5** in agent attempts.
The 2026-06-06 fix moved divergence from `MEM_addr1` to `MEM_addr2`,
shipped, and now the latest verifier run finds `MEM_value1` instead.
Each rule narrowing surfaces a new under-suppressed slot.

## Recommendation

Do not ship a same-layer corrective op. The right fix is upstream:
either:

1. Audit `layer14_mem_generation`'s V/O writes for the JSR-step-0
   MEM-value path. Confirm V[1+k]=OUTPUT_LO+k and V[17+k]=OUTPUT_HI+k
   resolve to 0x00 for non-byte-0 MEM_value cells when the JSR
   return-address is small (PC < 256).
2. Audit `layer14_jsr_mem_default_suppress` (l14_ops.py around
   `_jsr_mem_default_suppress`) — verify its predicate gates only
   `MEM_addr*` and never `MEM_value*`. The 06-06 finding says it
   cancels at all 4 addr-byte positions, but MEM_value cancellation
   would explain the new MEM_value1 leak.
3. Re-derive the L3 MEM DEFAULT +0.940 baseline. If it fires on
   `MEM_value` slots when it should not, the fix is at L3 (or its
   declarative-spec equivalent), not L14.
