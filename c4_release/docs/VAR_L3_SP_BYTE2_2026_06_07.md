# Var-Cluster Attribution — JSR Step 0 MEM_value1 (2026-06-07)

Wave 1 Cluster C1 follow-up: the prior memory note
`project_var_failure_mode_shifted` (2026-06-02) predicted the divergence
had migrated to L3 block=3 gen=13 SP_byte2 OUTPUT_LO[1]-vs-[0]. As of
2026-06-07 that prediction is stale — the failure has shifted again.

## Current divergence (verifier)

Running `tools/attribute_1096_failure.py` against `var_simple_0` and
`if_var_0`:

| Test         | step | slot       | expected | neural | suspect dims         |
|--------------|------|------------|----------|--------|----------------------|
| var_simple_0 |    0 | MEM_value1 |     0x00 |   0xff | OUTPUT_LO, OUTPUT_HI |
| if_var_0     |    0 | MEM_value1 |     0x00 |   0xff | OUTPUT_LO, OUTPUT_HI |

Both programs start with the function-prologue **JSR imm=3** at step 0,
pushing the return PC `0x0a` to `SP=0xFFFC`. Symbolic MEM_value bytes
are `(0x0a, 0x00, 0x00, 0x00)` — i.e. the high three bytes are zero.
Neural emits 0xff at byte 1.

This is the **same divergence shape** documented in
`docs/VAR_CLUSTER_JSR_PATH_FINDINGS_2026_06_06.md` but it has now moved
back from `MEM_addr2` (post the 06-06 partial fix) to `MEM_value1`.
Either the 06-06 patch was reverted/superseded, or a same-layer
competitor has shifted the surviving error to a different MEM slot.

op:        layer3_carry_forward_attn

reason:    declares produces['OUTPUT_HI']='<derived>' but residual

This is a **dynamic-verifier false positive** for step 0: head 5
(`_ax_full_relay_head_spec`, l3_ops.py:1427) reads
`OUTPUT_HI_PREV_STEP` via attention back to the prev-step AX-marker

zero. The verifier flags this as "claimed but silent" because it
cannot distinguish step-0 from a stale-residual bug.

## True writer of MEM_value1=0xff

Not localized by the verifier at step 0. Candidate writers per the
brief's "all candidate ops for suspect dims" list, intersected with
JSR-step-0 firing predicate (UPDATED 2026-06-08 after sub-agent
code-walk of `setup_helpers_l14.py:269-367` and
`l14_ops.py:407-641`):

- `layer14_mem_generation` head 5 (val_b1) — emits MEM_value1.
  **Now the prime suspect.** Heads 4-7 (val byte emitters) V reads
  `CLEAN_EMBED_LO+kk` / `CLEAN_EMBED_HI+kk` only (no `OUTPUT` add
  unlike heads 0-3, lines 619-623). For JSR, slot 1 (AX-source) is
  suppressed via `OP_JSR=-2*L` and slot 2 (STACK0-source) is enabled
  via `OP_JSR=+L`. The K for STACK0 mode at head 5 (val_b1) is **NOT
  `STACK0_BYTE1`** but rather BP-distance flags `H2+BP` minus
  `L1H4+BP` (lines 581-582). These BP positional flags are the ENT
  BP-frame byte-1 selectors. For JSR (push-PC) the STACK0 contains
  the return PC; the BP-frame selectors do not align with STACK0_BYTE1
  on the JSR path. Result: attention K-score for slot 2 collapses,
  softmax may degenerate to a default position whose CLEAN_EMBED
  carries 0xff token bits → emit 0xff at MEM_value1.
- `layer14_jsr_mem_default_suppress` — **EXONERATED.** Code review of
  `setup_helpers_l14.py:269-367` confirms the narrowed (2026-06-06)
  rule only fires at (a) MARK_MEM marker row (predicts addr_b0) and
  (b) `H1[MEM] AND BYTE_INDEX_0` (predicts MEM_addr1, per the L3 rule
  convention documented at line 247: `H1[MEM]+BYTE_INDEX_K` selects
  MEM addr bytes 1-3 for K=0,1,2). Neither predicate fires at any
  `MEM_value*` position. The earlier note in this doc speculating
  predicate-overlap was wrong.
- `layer16_lev_routing` — emits LEV bytes; does not fire on JSR.
- `tail_bit32_result_correction` — touches OUTPUT bytes but at a
  different layer-tail point; not gated to JSR-step-0 MEM_value.

The MARK_MEM marker emits addr_b0 prediction. MEM_value1 lives at
position d=5 (`val_pos[1] = (L2H0+MEM, H1+MEM)`). The L3 MEM DEFAULT
baseline +0.940 at OUTPUT_LO[0]/HI[0] PUSHES toward 0x00 here and is
not cancelled by any L14 suppress op for this position. So the 0xff
emission must come from a +X push at OUTPUT_LO[15]/HI[15] greater
than the +0.940 0x00 push. Head 5's V→O byte copy (no `-1.0` cancel
at the byte-0 slot, since the `o.append(AO(OUTPUT_LO+0,0,-1.0))` at
lines 627-628 is the `-1.0` of slot-0 CONST-K, not byte-0-token
cancel) writes `(softmax-weighted) CLEAN_EMBED_LO[kk]` to
`OUTPUT_LO[kk]` for kk=0..15. If the softmax-weighted K-position
embed has token=0xff (high nibble bits set), OUTPUT_LO[15]=high,
OUTPUT_HI[15]=high → argmax 0xff.

## Single-rule fix is not clear

Per memory note `feedback_single_rule_fixes_are_zero_sum`, narrow
DSL patches in this cluster have netted **0/5** in agent attempts.
The 2026-06-06 fix moved divergence from `MEM_addr1` to `MEM_addr2`,
shipped, and now the latest verifier run finds `MEM_value1` instead.
Each rule narrowing surfaces a new under-suppressed slot.

## Recommendation

Do not ship a same-layer corrective op. The right fix is upstream
in `layer14_mem_generation` head 5:

1. **Audit head 5 STACK0-source K (slot 2) for the JSR-only path.**
   At `l14_ops.py:580-582`, K positions are `H2+BP, -L1H4+BP`. This
   is the BP-frame byte-1 selector and is correct for ENT (which
   pushes BP). For JSR (which pushes PC, not BP) the corresponding
   STACK0 byte-1 selector should be the PC-byte-1 / STACK0_BYTE1
   position. Cross-check against vm_step legacy
   `_set_layer14_mem_generation` for the head-5 K positions on the
   OP_JSR branch — the migration may have collapsed the JSR/ENT
   distinction.
2. If head-5 K is correct for both JSR and ENT (i.e. STACK0_BYTE1
   ≡ the BP-frame byte-1 selector at this layer), then the
   regression is at the K-source for ENT being correctly aimed but
   the V data not yet routed by STACK0. Audit `STACK0_BYTE1` (or
   equivalent BP-frame H-flags) population at the L14 input
   residual: the upstream L7/L9 STACK0 attention may be silent for
   JSR step 0 (no prior frame).
3. (Existing point: re-derive L3 MEM DEFAULT — likely not the fix
   since MEM_value1 has no L3-DEFAULT competitor specific to it.)
4. **Exonerated**: `layer14_jsr_mem_default_suppress`. Do not
   narrow its gates further; it does not touch MEM_value1.
