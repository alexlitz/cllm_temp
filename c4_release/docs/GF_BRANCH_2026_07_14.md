# Green-field CRUX — depth=time control flow (JMP/BZ/BNZ)

**Date:** 2026-07-14 · **Branch:** `gf-branch` (off `greenfield-base`) ·
**Commit:** `565949c3` · **Lane:** green-field `c4_min/` control-flow CRUX.

This is the report for the flagged **OPEN RISK**: does the green-field's
**depth=time** substrate (each VM step = one transformer block) execute a program
whose instruction sequence depends on a **computed branch**? Answer: **YES.**
`JMP/BZ/BNZ` are implemented, pass the oracle, and a computed-predicate
`if-then-else` decodes byte-exact — with **no core-model change**.

---

## 1. The mechanism chosen: PC-driven per-block dispatch

The straight-line slice baked instruction `code[k]` into transformer block `k`
and ran it unconditionally. That cannot branch: with a computed PC, block `k`
does not know at compile time which instruction to run.

**Decision — Option B (PC-driven dispatch), not Option A (fixed unroll).** Each
unrolled block is a **universal VM step**: it reads the runtime `PC` scalar,
selects the instruction living at that PC from the baked code table, applies its
effect (which may itself set PC), and emits the step's AX. Because the executed
op is chosen by the *runtime* PC — not baked per position — a forward branch that
skips instructions Just Works: the block after the branch dispatches from the new
PC.

This runs on the **existing single-position depth=time substrate** (DESIGN.md
§(c)): the whole VM state lives in scalar residual bands at one position and
flows through depth via the additive residual. It is the cleanest fit and reuses
the exact-integer FFN rule compiler wholesale.

**Why not a content-match attention over a code table** (the general fetch)?
Because the pass-ceiling corpus (332 pure-minimal programs) has **bounded depth**
(max 36 steps, deep loops >40 excluded). A bounded unroll of universal
step-blocks — PC-driven selection *inside the FFN* — suffices. No cross-position
attention fetch is needed; attention stays identity, exactly as in the slice. The
task's own guidance confirms this: "BOUNDED depth (unroll to max steps) +
PC-driven instruction selection suffices; you do NOT need a recurrent/unbounded
solution."

### Per executed step = four pure-FFN blocks (single position, no attention)

```
1. FETCH    PC (scalar) -> PC_IS[i] one-hot  +  AX_ZERO predicate
2. DISPATCH rules gated on PC_IS[i] apply code[i]'s AX/STACK0 effect AND the PC update
3. FOLD     AX mod-256 (unconditional; no-op unless AX overflowed a byte)
4. EMIT     OUT_k <- AX ; HALT_SEEN_k <- cumulative HALTED
```

**FETCH** (`control.compile_pc_fetch`). `PC_IS[i] == (PC == i)` is an exact
integer one-hot from a unit triangular pulse
`tri_i(PC) = relu(PC-(i-1)) - 2·relu(PC-i) + relu(PC-(i+1))` (1 at PC==i, 0 at
every other integer), each `relu` the exact `silu(RELU_S·z)/RELU_S` identity.
`AX_ZERO == (AX==0) == relu(1-AX)` is the BZ/BNZ predicate. Bands are SET (not
incremented) via `silu`-identity self-clear units, so re-fetching each step is
idempotent under the additive residual.

**DISPATCH** (`control.dispatch_rules`). One `FFNRule` set per code index `i`,
guarded on the window `(PC_IS[i], 0.5, 1.5)` — fires **iff PC == i**. The AX/STACK0
data effect is **byte-identical to the slice's `_step_rules`**; only the guard
changed (from the always-on `ONE` to `PC_IS[i]`). Control flow adds **zero new
arithmetic**. The PC update is an extra write into `PC` (PC==i when it fires):

| op | PC write (gated on PC_IS[i]) | effect |
|----|------------------------------|--------|
| non-branch | `+1` | `PC := i+1` |
| `JMP t` | `+(t-i)` | `PC := t` |
| `BZ t` | `1 + AX_ZERO·(t-i-1)` | AX==0 → `t` ; else `i+1` |
| `BNZ t` | `(t-i) + AX_ZERO·(1-(t-i))` | AX!=0 → `t` ; else `i+1` |
| `HALT` | `+0` | freeze PC |

The branch algebra is the trick: a **single linear** write in the materialised
`AX_ZERO` band gives `t-i` when taken and `1` when not — no second-order gate.
Target `imm` is an **instruction index** (matches the reference oracle's
`resolve_static_target_idx`, which resolves `0<=target<len(code)` as an index).

**Depth = executed-step time.** The unroll length is `max_steps` (default
`2·n_code+4`). Block-group `k` is the k-th *executed* step, not the k-th
instruction; skipped instructions are simply never a step. `run` truncates the
emitted trace at the first step that executed `HALT` (via the `HALT_SEEN_k`
snapshot), so the returned trace length == the reference's executed-step count.

## 2. Validation

### 2a. `JMP/BZ/BNZ` flip to PASS on `run_oracle.py`

```
[PASS] JMP   1/1     [PASS] BZ    2/2     [PASS] BNZ   2/2
[PASS] ADD 4/4  [PASS] SUB 4/4  [PASS] PSH 2/2  [PASS] IMM 3/3   (unchanged)
OP-CLASS PASS: 7/30   (was 4/30)
```

Both branch directions pass — taken (`bz_taken`/`bnz_taken`) and not-taken
(`bz_nottaken`/`bnz_nottaken`) — matching **both** the exit code and the executed
**step count** (the oracle checks `steps` for the RealBackend). **No regression**
in the four previously-passing op-classes.

### 2b. Real if-then-else with a COMPUTED predicate

`if a==b then X else Y` compiled the way the C4 compiler emits a comparison-branch
(comparison via subtraction, then a zero-test branch):

```
idx: 0        1     2        3      4       5       6       7       8
     IMM a ;  PSH ; IMM b ;  SUB ;  BZ 7 ;  IMM Y ; JMP 8 ; IMM X ; HALT
     \_______ AX = a-b (0 iff equal) ______/  \__ else __/  \_then_/
```

The branch depends on the **runtime** `a-b`. Result (byte-exact vs the reference
interpreter, correct branch + correct trace length):

| a,b | branch | trace | exit | ✓ |
|-----|--------|-------|------|---|
| 5,5 | THEN | `[5,5,5,0,0,111,111]` | 111 | ✓ |
| 5,7 | ELSE | `[5,5,7,254,254,222,222,222]` | 222 | ✓ |
| 9,9 | THEN | `[9,9,9,0,0,42,42]` | 42 | ✓ |
| 3,8 | ELSE | `[3,3,8,251,251,99,99,99]` | 99 | ✓ |

The ELSE path correctly runs one extra step (the `JMP`); the not-taken branch's
instructions are correctly skipped. This is the mission's `if a<b then X else Y`
shape (the C4 compiler lowers `<`/`==` to a compare-then-branch; the branch
*mechanism* is what this lane owns — the CMP-result-in-AX op is separate op-rule
work, out of scope here).

substrate architecture (DESIGN.md §(e)) already supports control flow without a
core rework. **Consolidation flag:** none required; the change is self-contained
in `control.py` + a thin router in `compiler.py`.

## 4. Verdict — the 332 ceiling is REACHABLE (control flow is not the blocker)

The 332 pure-minimal corpus's only control-flow need is **forward branches** (the
if-family: `if_gt/lt/eq/var`), and it has **no unbounded loops** (max 36 steps).
This mechanism handles arbitrary forward `JMP/BZ/BNZ` within the bounded unroll
(and backward targets too, by the same PC write). So **control flow is not a
blocker to the 332 ceiling.** The remaining gap to the ceiling is per-op-class
*compute* — CMP result → AX (0/1), bitwise, shift, memory (LI/SI), and the
calling convention (JSR/ENT/LEV, task #518) — each independent op-rule work that
plugs into the same PC-driven dispatch (add the op's AX/STACK0 write to
`dispatch_rules`; the PC update is already generic).
