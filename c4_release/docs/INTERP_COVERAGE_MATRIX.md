# Interpreter-vs-Neural Coverage Matrix (full 1096)

**Question:** across the FULL 1096 corpus, what fraction can the faithful **CPU** gate (`tools/interp_oracle_gate.py`) authoritatively test vs what is irreducibly GPU-only? This makes the *"everything testable on the interpreter"* vision concrete and bounds the CPU/GPU boundary.

Per program, two verdicts are cross-tabulated:

- the **CPU gate verdict** — `interp_oracle_gate.classify_program`, the value-faithful single teacher-forced forward over the production `alu_mode='efficient'` model, executed entirely on CPU (`CUDA_VISIBLE_DEVICES=""`); and
- the **neural full_trace ground-truth** (the AUTHORITY) — the pure-neural batched decode from `tools/run_1096_canonical.py --criterion full_trace --spec-k 0`, read from `/tmp/1096_uncapped.json` (criterion=full_trace, spec_k=0, cap=100000).

**Gate version measured:** RECONCILED main gate (post-ALU-execution ac61a87b + clean-ALU cross-step reconciliation) — the real composite ALU blocks are EXECUTED on CPU AND an ALU program whose own (PC, AX) decodes cleanly / whose divergence lands on the ALU step itself is CERTIFIED (PASS or HIGH-confidence FAIL, category 2) rather than blanket-deferred CROSS-STEP behind an unrelated upstream SP/STACK0 re-anchoring correction. The cross-step guard stays intact for the non-ALU var/func/if framing-drift

**Scope:** ALL 1096 programs (merged from a 16-way CPU shard run, gate --max-steps 14 which is verdict-identical to 48: all neural-PASS finish <=12 steps, all neural-FAIL diverge <=6) — 1096 programs evaluated.  
**Generated by:** `tools/interp_coverage_matrix.py`.

## Cross-step reconciliation — what clean-ALU certification lifted

All **299 cat-2 ALU programs are now CERTIFIED** (215 PASS + 84 HIGH-confidence FAIL); **0** remain deferred CROSS-STEP. Before the reconciliation the blanket cross-step poisoning guard deferred essentially every ALU program (mul/div/mod/expr) because an unrelated upstream step-1 SP-byte-2 / STACK0-high-byte re-anchoring correction fired first — so this is the concrete deferred→certified lift:

| reconciliation effect | count | neural-confirmed |
|-----------------------|------:|-----------------:|
| ALU program moved deferred→certified **PASS** (clean ALU: every (PC, AX) matched the oracle, the benign SP/STACK0 re-anchoring does not poison the ALU result) | 215 | 197 neural-PASS (true) / 18 neural-FAIL (residual) |
| ALU program moved deferred→certified **HIGH-confidence FAIL** (the flat divergence lands on the ALU opcode step itself — the GENUINE first divergence, coarse block-attributed) | 84 | 84/84 match a neural FAIL |

**Soundness of the lift:** of the 215 certified-PASS ALU programs, 197 are confirmed PASS by the neural authority and **18 are gate-PASS / neural-FAIL** — the irreducible residual. Those 18 are programs whose ALU RESULT the single teacher-forced forward decodes CORRECTLY at every step (the model emits the right value under teacher forcing) yet production's autoregressive decode poisons a downstream step; two such programs (e.g. a clean 21*59 that PASSES and a 9*98 that FAILS) are BYTE-IDENTICAL in the CPU flat decode, so no single-forward CPU gate can separate them. They are the honest cost of certifying clean ALU on CPU (a false-trust the GPU `--faithfulness-check` resolves), and are counted against the cat-2 soundness below. The cross-step guard stays fully intact for the NON-ALU clusters (var/func/if PC framing-drift): cat-1 has 0 false-trusts.

## Soundness — does the CPU gate verdict match the neural authority?

Within each CPU-testable bucket, the agreement rate between the gate's PASS/FAIL and the neural full_trace pass/fail. This is the number that makes the CPU gate trustworthy as a stand-in for the GPU run. (Programs with no comparable neural verdict — deep-loop neural `error` — are excluded from the denominator.)

| Bucket | gate PASS/FAIL | verdict agree w/ neural | of mutual FAILs, same div-step |
|--------|---------------:|------------------------:|------------------------------:|
| 1 CPU-testable + rule-attributed | 9P / 189F | 197/198 = 99.5% | 188/188 = 100.0% |
| 2 CPU-testable, coarse ALU | 215P / 84F | 281/299 = 94.0% | 33/84 = 39.3% |
| **COMBINED CPU-testable** | | **478/497 = 96.2%** | |

Two honesty caveats on the soundness number:

- **Verdict (PASS/FAIL) agreement** is what the 96.2% measures. The **div-step** agreement among mutual FAILs is LOWER (cat 1: 100.0%, cat 2: 39.3%): when both the gate and the neural model FAIL, they frequently disagree on WHICH step diverged first — the gate's single teacher-forced forward "recovers" the early autoregressive divergence and surfaces a later flat-decode mismatch instead. So the gate is a reliable PASS/FAIL oracle but a WEAKER step-localizer on the multi-step fails.
- A handful of CPU-testable programs are gate-PASS / neural-FAIL (the disagreement table below): the single forward passes them but the autoregressive decode poisons a later step the flat forward never sees. These are the real soundness residual within the CPU-testable buckets.

For the **GPU-only** bucket (cat 3), the gate's LOW-confidence FAIL matches a neural FAIL 414/596 = 69.5% of the time — i.e. the gate correctly DEFERS rather than over-claiming: where it cannot single-forward resolve, it does not pretend to. The cases where the neural model PASSES are exactly the cross-step re-anchoring the flat forward mis-reads (a true GPU-only resolve). The gate never attributes a rule for these (LOW-confidence), so the mis-flag costs no false fix target.

## Answer: how much of 1096 is CPU-testable on the interpreter?

**497/1096 = 45.3% of the corpus is CPU-testable** by the post-ALU-execution gate (cat 1 rule-attributed + cat 2 coarse-ALU), with the gate-vs-neural verdict agreeing 96.2% of the time on the comparable set — that is the soundness floor for using the CPU gate instead of the GPU run.

The irreducible **GPU-only boundary is 599/1096 = 54.7%** (cat 3): the autoregressive cross-step framing-drift / AX-high-byte re-anchoring a single teacher-forced CPU forward provably cannot reproduce. The gate FLAGS every one of these (LOW-confidence) and points at the GPU `--faithfulness-check`; it never silently mis-attributes them. This is the concrete CPU/GPU boundary.

**Bounded honesty (what the CPU authority CANNOT give):** cat-2 ALU FAILs are attributed to the ALU BLOCK, not a declarative rule (the blocks are imperative); AX-high-byte / SP/BP/STACK0 cross-step divergences are cat 3 (GPU-only, not rule-attributed); and attention/relay roots surface as "no runtime FFN writer" within cat 1 (CPU-testable verdict, but the wrong value is upstream of any FFN so no rule is named). These are categorized as such — the tool never claims an attribution the gate cannot produce.

## Provenance & reproduce

**Neural ground-truth cache.** The neural verdicts come from `/tmp/1096_uncapped.json` (criterion=full_trace, spec_k=0, n_results=1096). It was VALIDATED against the current model HEAD by re-running a 10-program id sample through `run_1096_canonical.py` — status + divergence_step matched all 10 (`add_0`, `add_1`, `add_2`, `var_simple_0`, ids 250/500/550/800/975 …). Every neural FAIL diverges by step ≤6 and every neural PASS is ≤12 declarative steps (measured over all 1096), so the gate's decode window covers all comparable verdicts (no windowing artifact); the CPU run used `--max-steps 14`, which is VERDICT-IDENTICAL to 48 (validated: a deep 48-step loop, var, func, nested, and ALU program all decode to the same PASS/FAIL/div-step at cap 14 vs 48) but ~3-4× faster on the deep loop/gcd/rec band. Regenerate the neural cache with:

```
CUDA_VISIBLE_DEVICES=0 python tools/run_1096_canonical.py \
    --criterion full_trace --spec-k 0 --max-steps-cap 100000 \
    --output /tmp/1096_uncapped.json
```

**CPU gate run.** The CPU gate verdicts were produced ENTIRELY on CPU (`CUDA_VISIBLE_DEVICES=""`), sharded 16-way for parallel fan-out (each program is a ~5-30s `faithful_full_forward`; the deep loop/gcd/rec band dominates). Reproduce:

```
# 16-way CPU shards (no GPU):
for k in $(seq 0 15); do
  CUDA_VISIBLE_DEVICES="" OMP_NUM_THREADS=3 python tools/interp_coverage_matrix.py \
      --neural-json /tmp/1096_uncapped.json --shard ${k}/16 \
      --out-json /tmp/cov_shards/shard${k}.json &
done; wait
# merge -> final matrix + this markdown:
python tools/interp_coverage_matrix.py --neural-json /tmp/1096_uncapped.json \
    --merge '/tmp/cov_shards/shard*.json' \
    --out-json /tmp/coverage_matrix_full.json \
    --out-md docs/INTERP_COVERAGE_MATRIX.md
```

A single unsharded `python tools/interp_coverage_matrix.py --neural-json … --out-md …` run is equivalent but takes ~2-3h on CPU; the sharding is purely a wall-time optimization (the verdicts are shard-independent). `--sample N` runs a quick cluster-round-robin slice (clearly NOT full coverage). NO production weights/ops are touched — this is INFRA/measurement only.
