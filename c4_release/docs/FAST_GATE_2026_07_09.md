# Fast faithful corpus gate (`tools/fast_gate.py`) — 2026-07-09

**Goal.** Predict the **full-1096 full_trace pass-delta** of a campaign fix in
**~10-15 min** (two GPUs) instead of the **~2 h** full run, so fixes iterate in
minutes. The decisive requirement: **catch the `C4_DERIVE_ADDSUB` −34** that the
old 72-program `tools/flag_regression_gate.py` MISSED.

**Tooling only — golden `e50521f3` untouched.** The gate only spawns the
existing `tools/run_1096_canonical.py --criterion full_trace --spec-k 0`
subprocess; it never writes weights.

---

## Why the old 72-prog gate missed the ADD/SUB −34

`C4_DERIVE_ADDSUB` re-derives ADD/SUB byte-0 and **reroutes the shared L10
OUTPUT byte-1 bus** (its integration fix demuxes `_l10_add_high_byte_adder_
rules` + `tail_bit32_result_correction` onto a private `ADDSUB_TAIL_SINK` band).
That touches **every multi-byte consumer** on that bus, not just add/sub. Its own
smoke sample was 13/13 clean and 5/6 add-sub passed — but the full-1096 net was
**−34** because the regression is **spread** across add/sub AND the multi-byte
consumers (mul/div/mod/var/expr/nested/absdiff).

The 72-prog gate had only **4 add + 4 sub** and one representative for most other
clusters, with **no pass/fail balance and no population weighting**. A −34 spread
thinly across ~10 clusters is invisible at 1-4 samples/cluster.

## Sample design (`tools/fast_gate_sample.json`, 220 ids, all 56 clusters)

Stratified, weighted toward the regression-prone families the miss exposed, and
**runtime-bounded**. A program's decode cost scales with its **divergence step**
(fail-fast) × the un-windowed O(steps²) forward, so the wall-time drivers are the
16-39-step *failing* programs (var, func, absdiff, nested) — NOT the arith band
(which diverges at ≤5 steps). The −34 the gate must catch is dominated by the
**cheap** shared-OUTPUT-bus ALU families + var, so those stay heavy and the
expensive deep/late-diverging clusters are capped:

| tier | clusters | n each | ~steps | why |
|------|----------|-------:|-------:|-----|
| **ALU-bus (heavy)** | add, sub, mul, div, mod | 12 | ≤8 (cheap) | the shared-OUTPUT-bus ALU families a byte-1 reroute hits directly |
| **MEM-SMOKE (cheap)** | var_simple | 10 | 7-11 | SI/LI store-load path can never silently break |
| **MEM-SMOKE (mid)** | var_mul, var_update | 6 | ~17 | same; capped (uniformly 17-step) |
| **MEM-SMOKE (deep)** | var_three | 5 | ~25 | same; capped (the mid-band wall) |
| **consumer (cheap)** | expr_add_mul/paren/mul_div/mod | 8 | ~8 | multi-byte results flow through the same byte-1 cascade |
| **consumer (mid)** | absdiff | 4 | ~24 | same; capped |
| **consumer (deep)** | nested_quad (31), nested_sumsq (39) | 3 | 31/39 | same; capped tightest |
| **if / bool** | if_gt/lt/eq/var, bool_and | 6 | ~10 | broad per-step-root coverage |
| **func** | func_identity/add/mul/square/max/min | 4 | ~13-15 | per-step-root coverage; capped (late divergence) |
| **deep sentinels** | loop_*, rec_*, gcd | 2 | 41-8369 | tracked (decoded as `skipped` at `--max-steps-cap 40`, free) |
| **edge** | the 22 edge_* clusters | 1 | ≤8 | one representative each |

Total **220 ids** (160 cheap ≤15-step, ~50 mid 16-25, 10 deep 26-39, 6 skipped
sentinels). When an **OFF-baseline full-1096 verdict json** is passed to
`--regen-sample --baseline-json`, each cluster's budget is split ~**half pass /
half fail** so a regression (ok→fail) AND a gain (fail→ok) are both observable.
Without it (the shipped default), the sample is a deterministic short-member
stratification (still covers every cluster + over-weights the regression-prone
families).

### The narrow `--clusters` inner-loop

For iterating on one fix, `--clusters add,sub,mul,div,mod,expr_*,var_simple`
(the 102 CHEAP regression-detectors, all ≤9 steps) runs in **~8 min** concurrent
and already catches the ADD/SUB −34 (see the calibration table). Run the full
220-id sample once before landing.

## Prediction math

Per cluster, `sample_net = flips − regressions`, scaled to the full corpus by
`cluster_population / decoded_sampled_count`. Summed across clusters →
**predicted full-1096 delta**. This is what the 72-prog gate could not do: it had
too few samples AND no population scale-up, so a spread −34 rounded to ~0.

**Envelope (honest):** the gate predicts the **sign** and the **rough magnitude**
(order-of-magnitude / decisive block-or-not), NOT an exact count. The scale-up
assumes the sampled subset's regression rate ≈ the cluster's full rate; a fix
whose damage is concentrated in the *un*-sampled members of a cluster is
under-counted (mitigated by the heavy 12/24-per-cluster sampling on the ALU-bus
families and the pass/fail balance).

## Runtime (measured, RTX A5000 x2, `--criterion full_trace --spec-k 0`)

| run | ids | wall (concurrent 2-GPU) |
|-----|----:|------------------------:|
| null (arith+var_simple) | 70 | **4.3 min** |
| ADD/SUB inner-loop (`--clusters` cheap 102) | 102 | **8.4 min** |
| full 220-id sample | 220 | **~12-15 min** (est.; the 16-25-step var/func mid-band is the driver) |

Cost model: **~40 s cold bake + ~1.6 s/cheap-program**; the 16-25-step *failing*
programs (var/func/absdiff) are ~10-15 s each and the 31/39-step nested_* run
solo. With **two GPUs** the OFF and ON states run **CONCURRENTLY** (one per GPU)
so total wall ≈ one state; on a single GPU the two states run back-to-back
(~2× per-state). Use `--mem-step-scale 0.5` when co-existing with another GPU job
(avoids the OOM-retry batch-halving that otherwise 3-4×'s a chunk). Versus the
**~2 h** full-1096 run this is a **~8-16× speedup** — the loop-unblocking win.

## Calibration table (predicted vs actual full-1096 delta)

Run identically on the `derive-addsub` tree (base `59a9de19`), `--criterion
full_trace --spec-k 0 --max-steps-cap 40`, concurrent 2-GPU.

| case | flag | actual full Δ | gate net (sample) | gate **predicted** Δ | verdict | gate result |
|------|------|-------------:|------------------:|--------------------:|---------|-------------|
| **ADD/SUB (the miss)** | `C4_DERIVE_ADDSUB=1` | **−34** | −10 (12 reg / 2 gain) | **−44** | REGRESSION | **CAUGHT** — right sign, right order of magnitude (the 72-prog gate reported CLEAN) |
| null (self-consistency) | `C4_FASTGATE_NULL_NOOP` (no-op, OFF vs ON) | 0 | +0 | **+0** | clean | correct — no false positive; deterministic bake across separate caches |
| JSR BP byte-3 | `C4_JSR_BP_BYTE3_CLEAR` (0 vs 1) | ~0 | +0 | **+0** | clean | correct — verdict-neutral on the sampled func + arith clusters (58 ids; its func gains already saturated at this baseline) |

**The decisive line is row 1:** on the 102-id cheap regression-detect subset the
gate reports **12 add/sub regressions** (ids `0,4,8,20,25,29,33,37,45` in add;
`54,75,83` in sub) and only 2 gains → sample net **−10**, population-scaled to a
**predicted −44**. That is the SAME SIGN and rough magnitude as the actual
full-1096 **−34** — the regression the old 72-program gate reported as **clean**
(it had only 4 add + 4 sub, no population scale-up). Row 2 proves the gate has no
false positive on an identical build.

Note the gate slightly OVER-predicts (−44 vs −34): the cheap subset over-samples
add/sub (12/50) relative to the whole corpus and catches a high per-cluster
regression rate; the full 220-id sample tempers this by decoding the passing
multi-byte consumers alongside. For a go/no-go BLOCK decision the sign + magnitude
is decisive — which is exactly what iterating in minutes requires.

## Usage

```
# Gate a fix behind its kill-switch flag (predict the full-1096 delta):
python tools/fast_gate.py --flag C4_DERIVE_ADDSUB

# Gate HEAD vs a base commit (branch not behind a single flag):
python tools/fast_gate.py --base 59a9de19

# Narrow while iterating:
python tools/fast_gate.py --flag C4_MY_FIX --clusters add,sub,mul,var_mul

# Regenerate the pass/fail-balanced sample from an OFF-baseline full run:
python tools/run_1096_canonical.py --criterion full_trace --spec-k 0 \
    --max-steps-cap 40 --output /tmp/off_full.json
python tools/fast_gate.py --regen-sample --baseline-json /tmp/off_full.json
```

Exit code is non-zero iff any cluster regressed (ok→fail) — a CI/pre-merge block.
