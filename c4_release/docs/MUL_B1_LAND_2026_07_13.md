## What this note is — a RECONSTRUCTION onto the fold, not a new fix

The fix was originally built on branch `mul-b1-delivery` (commit `781addcc`,
`docs/MUL_B1_DELIVERY_2026_07_13.md`) **before** the EMIT-G5 fold. The original
added an `OP_MUL`/`OP_SHL` W_up blocker (−30, S-scaled) to the **four**
hand-written `_layer14_jsr_ax_bytes_zero_rules` clear units + extended
`make_layer14_jsr_ax_bytes_zero_op`'s `reads` set.

Current main (`f5051c8d`) FOLDED those four ops (`layer14_{jsr,lc,alu_nocarry,ent}
_ax_bytes_zero`) into ONE spec-driven generator (EMIT-G5, commit `356e7e80`):
`_AxBytesZeroSpec` + `_ax_bytes_zero_rules(spec, S)` + the `_AX_BYTES_ZERO_SPECS`
table. This note reconstructs the identical semantics onto that fold.

### The root (unchanged — proven on `781addcc`, spec_k=0 faithful-autoregressive)

The wide-MUL byte-1 relay (`layer15_alu_high_byte_relay` head 8) already
stages+delivers the derived result byte 1 (`AX_FULL+5 → OUTPUT+5`, ×W_o 20 =
+40) **identically** for the passing (idx110/idx100) AND failing (idx104/idx106)
muls — head-8 is NOT the failure. idx104/106 drop byte 1 because block 37
(physical) / logical-L14 `layer14_jsr_ax_bytes_zero` **mis-fires**: those two MUL
byte-1 emit rows carry a spurious `OP_JSR` residue (~0.22), and the 30-token
campaign frame amplifies the `OP_JSR` gate weight to 40, so
`silu(0.22·40)=silu(8.85)` fires the JSR AX-bytes-zero clear HARD → OUTPUT
slammed to the byte-0-default → byte 1 = 0x00. The passing muls have
`OP_JSR ≈ 0` there.

## The reconstruction (l14_ops.py, on the folded structure)

The fold keeps each op as its own 4-unit range (`layer14_jsr_ax_bytes_zero`
is one spec). The blocker is applied **only to the JSR spec** — matching the
original semantics (the clear must not zero a genuine MUL/SHL byte-1 result):

1. `_mul_b1_delivery_enabled()` — the `C4_MUL_B1_DELIVERY` flag helper.
2. `_AxBytesZeroSpec.__init__` gains a `mul_b1_blocker=False` field.
3. `_ax_bytes_zero_rules(spec, S)`: when `spec.mul_b1_blocker and
   _mul_b1_delivery_enabled()`, splice `("OP_MUL", -30.0), ("OP_SHL", -30.0)`
   into `common_conditions` (shared by all 4 clear units of that spec) —
   evaluated at bake time, mirroring the `gate_weight_fn` idiom so the flag
   gates cleanly with no import-time state.
4. `_make_ax_bytes_zero_op(spec)`: extend the op `reads` set with
   `{"OP_MUL", "OP_SHL"}` under the same guard.
5. `_AX_BYTES_ZERO_SPECS["jsr"]` sets `mul_b1_blocker=True`. The lc / alu_nocarry
   / ent specs leave it `False` (default) — no change to those three ops.

`up = S·(IS_BYTE + H1+1 − 30·OP_MUL − 30·OP_SHL − threshold)`. On a MUL row
(`OP_MUL=0.22`) that drives `up` far negative → `silu(up) ≈ 0` → the clear does
not fire → head-8's +40 lands → byte-1 emitted. On a **genuine JSR row**
`OP_MUL == OP_SHL == 0`, so `up` (and every write) is byte-for-byte unchanged.
